## PDF: dipendenze e scelta da verificare

Nel repository è installato `puppeteer-core@25.1.0`; non risultano `pdfkit`, `pdf-lib`, Playwright o React PDF tra i pacchetti installati. Puppeteer-core richiede un eseguibile Chromium separato: il runtime Render non dimostra di averlo. I biglietti ESC/POS non sostituiscono un PDF. Due spike ammessi: PDF vettoriale tramite libreria gratuita aggiunta esplicitamente con font verificati, oppure renderer Chromium impacchettato e autorizzato dal contratto deploy. Verificare memoria, font licenze/Unicode, timeout e nessuna dipendenza dal Chrome dell'utente. Non usare automazione shell/browser per QA visiva; eventuale rendering PDF come artefatto deve seguire il workflow PDF, e la UI va verificata tramite CUA.

Contratto dati/API prima di scrivere i test; limiti concreti di loop: batch piccolo → build/typecheck → test meaningful → verifica avversariale → massimo due riparazioni, poi documentare blocco e tornare alla scoperta.

QA browser tramite CUA su webapp Tako propria e tenant QA esplicitamente dedicato: titolare desktop/mobile, editor, agenzia multi-tenant, cliente; navega, compila, conferma e verifica feedback reale, reload/sessione, errore/loading, tastiera/focus, rete assente, click rapidi. Menumal cliente escluso da qualsiasi azione di scrittura. Registrazione reale se si dichiara conformità del movimento; screenshot statico prova solo layout. CUA non espone automaticamente export PDF: registrare separatamente ciò che è effettivamente verificabile.

Gate di rilascio: copertura sopra con risultati pass/failed/blocked e motivazione; build frontend/server; migrazioni verificabili senza alterare dati originari; test due tenant; browser smoke nuovo e rollback documentato; delivery/provider reali solo se accessi verificati. Un componente visuale, una route stub o un test mock-provider passato non valgono funzionalità completa. Nessun claim “parità completa” finché i gate materiali restano aperti.
