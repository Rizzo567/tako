# Tako originale — discovery backend per parità Menumal

Data: 2026-10-10. Discovery READ ONLY sul codice; nessuna migrazione applicata, scrittura remota, nuovo hosting o modifica delle credenziali. Questo documento definisce contratti proposti, non funzionalità già disponibili.

## Base osservata e limiti

- Operational HTTP: `apps/server/src/index.ts`, autenticazione cookie DB e Socket.io. `TAKO_MODE=web` è distinto dal control-plane `TAKO_MODE=cloud`.
- Identità operative: `schema/users.ts`, `routes/auth.ts`, `routes/staff.ts`; tenant derivato da sessione, hash importati preservati. Registrazione pubblica disabilitata. Il control-plane possiede token verifica/reset separati (`schema/cloud/tokens.ts`) e non va collegato assumendo che identità operative e cloud coincidano.
- Menu: `schema/menu.ts`, `routes/menu.ts`, `routes/customer.ts`. Più menu già persistibili ma cliente pubblico legge solo il primo attivo; editor non dispone di API PATCH/DELETE menu o selezione pubblica per menu. Sezioni singolo livello; prezzi base e modificatori varianti reali. Non chiamare nuovo ciò che già esiste.
- Traduzioni: tabella `menu_item_translations` con PUT/GET/DELETE staff; JSON legacy `nameTranslations`/`descriptionTranslations` anche su item e sezioni; cliente legge traduzioni separate in `routes/menu-i18n.ts`. Servono una sola precedenza e migrazione non distruttiva.
- Impostazioni: `routes/restaurants.ts` merge JSONB; colore/logo/timezone/lingue/recensioni disponibili. Nessun sistema completo di stile, gallery, versioni, PDF o statistiche scansioni.
- Immagini: upload autenticato, magic bytes/re-encode/quota in `lib/image-store.ts`; storage Supabase privato dietro `lib/remote-image-store.ts` e proxy pubblico `routes/remote-images.ts`. Nessun indice asset/lista metadata/delete tenant.
- Prenotazioni: `schema/reservations.ts`, `routes/reservations.ts`, customer route; calendario/status/conflitti tavoli già presenti, timezone tramite helper delle route (verificare confini DST: intervallo locale non equivale a +24h). Reminder, riconferma, depositi e integrazione Google assenti.
- WhatsApp rimane ultimo blocco: attuale Baileys è globale e disabilitato nel runtime web. Non può diventare multi-tenant mediante semplice riattivazione.
- Originale migrato conserva UUID, hash e storico; sessioni native escluse. Supabase è database dedicato operativo; route usano connessione privilegiata, quindi filtri tenant applicativi restano obbligatori.

## Invarianti dei nuovi contratti

1. Ogni risorsa privata porta restaurantId e deriva tenant dal principal, mai da un body non autorizzato. Risposte 404 per UUID di altri locali. Per agency/multi-locale il tenant di destinazione deve corrispondere a membership attiva esplicita, non a UUID arbitrario.
2. Prezzi in tipi money esistenti; orderItems mantengono nome/prezzo al momento dell'ordine. Restore menu non riscrive ordini/conti né UUID referenziati.
3. Contratti `GET -> {data,revision}`; mutazioni `If-Match`/revision obbligatoria dove c'è concorrenza editoriale, 409 con versione corrente; update e audit/versione nella stessa transazione.
4. Storage token e segreti provider solo backend. Test isolati prima di migrazioni; nessuna prova di scrittura su Menumal cliente.
5. Bozze, pubblicazione e disponibilità operativa sono stati distinti: esaurito deve agire subito, mentre una bozza non cambia menu pubblico o PDF pubblicato.
6. Menu cliente, ordine, PDF, QR e traduzioni usano la stessa proiezione pubblica e lo stesso clock timezone. Mai ordine accettato per un piatto escluso dalla schedule dopo il caricamento.

## Revisioni, visibilità e pubblicazione

Il minimo schema sicuro evita un fork completo degli ordini: aggiungere stato editoriale e tombstone alle entità menu, con snapshot pubblicato separato e revision atomica. La proiezione può inizialmente interrogare tabelle versionate, purché edit in bozza non alteri prezzo pubblico. Prima di implementare decidere se draft/live convivono come JSON snapshots o righe revisionate: entrambe richiedono che order pricing legga la versione pubblicata corrente. Conservare sempre il legame al menuItemId originale. Non basare storico e restore su reimport con UUID nuovi.

Sezioni nidificate: parentSectionId null è una categoria; parent è una categoria dello stesso menu; limitare profondità a due livelli per parità richiesta. Endpoint di reorder accetta intera sequenza scoped (no ID foreign, duplicati, omissioni involontarie). Visibilità temporale calcolata alla richiesta senza cron fragile; realtime pubblica nextVisibilityChange così browser rifetcha al boundary.

Cataloghi: osservazione Menumal indica 35 caratteristiche/13 additivi, non ne conosciamo qui le definizioni canoniche complete. Non inventare etichette per raggiungere un numero; acquisire elenco autorizzato dalle fonti già raccolte o definire esplicitamente catalogo Tako distinto. HACCP: servono contenuti/forma documentale effettivi, non basta chiamare un PDF "HACCP".

## Gate finale e fallimenti espliciti

- Nessun "tutto Menumal" se uno dei B01–B19 è solo placeholder. Ogni gate deve contenere prova automatica e prova UI reale quando pertinente; B18/B19 external hosting possono essere separatamente dichiarati bloccati con capacità concreta mancante.
- Migrazioni additive dry-run su clone; conteggio righe/UUID/hash/storico invariato, backup verificato; apply reale solo dopo gate. Restore non cancella ordini di un piatto tolto.
- Test backend capability e IDOR, renderer PDF visivo, API customer preview/save, complete path edit->publish->QR->order->KDS->bill, QR metriche, multi-locale switch, reset credentials.
- Max due correzioni per gate fallito; poi root riapre discovery con errore e criterio di risoluzione, senza retry cieco o perdita dati.
- Provider email, OCR/AI, gateway card, Google reservation integration e DNS sono dipendenze verificabili. Non creare servizi a pagamento o dichiarare integrazione attiva senza accesso reale/sandbox. Link prenotazione da Google non equivale a integrazione nativa Reserve with Google.
- Hosting pubblico resta rinviato: localhost non abilita clienti/camerieri su altri dispositivi, redirect email pubblici, domini agency o callback gateway esterni. Collaudi isolati sono possibili, rilascio esterno no.

## Evidenze QA integrate e contratto implementativo

La discovery QA in `qa-discovery.md` identifica bug reali: traduzioni pubbliche filtrano availability ma non menu/sezione attivi; capienza prenotazioni non impedisce partySize oltre seats; giornate DST usano +24h invece del prossimo giorno locale. Questi sono gate di correttezza obbligatori oltre alle nuove feature.

Contratto scelto: `lib/menu-workspace-contract.ts`, snapshot JSON draft/published per tenant; route additive `/api/menu-workspace`; schema SQL in `menu-workspace.sql`. Publish riconcilia tabelle operative preservando ID/storico. Nessuna bozza raggiunge pricing pubblico. Customer route, autenticazione multi-locale e integrazione migrazioni restano ownership root.

## Implementazione verificata (batch backend 2026-10-10)

Il contratto stabile è `apps/server/src/lib/menu-workspace-contract.ts`, plugin `/api/menu-workspace` in `routes/menu-workspace.ts`. Cinque tabelle additive in `menu-workspace.sql`; PDF preset personali sono snapshot `pdfPresets[{id,name,config}]`, non nuove tabelle. Draft, published e versioni sono separati. Publish riconcilia gli ID originari e conserva esaurito operativo quando l'editor non cambia esplicitamente disponibilità, con lock delle righe.

- GET/PUT workspace; POST publish; GET/POST versions; GET diff con dettagli nome/tipo/campo/before/after; POST restore in bozza. Before è bozza corrente, after versione selezionata.
- GET/POST/DELETE presets stile; GET/POST/DELETE assets; inventory effettivo anche per immagini non assegnate, usage/quota e riferimenti live/draft/versioni. Delete di asset usato risponde409. Metadata upload misura il file dopo re-encoding.
- GET catalogs (catalogo Tako dichiarato); GET analytics aggregate; public event helper idempotente senza PII grezza. Parent integra evento/proiezione in route pubbliche.
- POST import/preview CSV RFC4180 con mapping oppure JSON completo; nessuna scrittura preview. POST import/confirm salva bozza con expectedRevision; foto/PDF/OCR/link non diventano import riusciti senza provider e review reali.
- POST translate/preview usa Groq esistente solo su azione esplicita, max200 etichette mancanti e3 richieste/minuto. Provider assente503, fallimento502 e nessuna scrittura. Test provider mocked, nessuna chiamata pagata/QA; traduzioni manuali conservate. Conferma tramite PUT revisionato. Food labels tradotti via foodTranslations.
- POST pdf genera PDFKit vero con font Noto OFL inclusi (Latin/Greek/Cyrillic + Arabic/Hebrew), impaginazione esplicita colonne, quattro margini, interruzioni categoria, logo, immagini tenant, copertina, legende, QR e footer. Font per altre scritture non sono dichiarati verificati. Campi digital style/PDF osservati sono typed/validati, niente CSS/HTML arbitrario.
- GET qr PNG/SVG generale/menu pubblicato attivo del tenant, WEB_ORIGIN condiviso; PNG decodificato indipendentemente con Apple Vision, payload corrispondente.
- Voce web: browser SpeechRecognition dopo gesto, fallimento/assenza API con campo testo disponibile; nessun socket appliance, PCM upload o esecuzione automatica. Backend locale originale conservato dopo detection runtime. QA con SpeechRecognition mock, nessuna cattura microfono reale.

Verifica locale: 19 test focused verdi su DTO/DST/diff/PDF/import/providerpreview/voce/QR; build server verde. PDF fixture 35 piatti + testo lungo, tre pagine/2colonne renderizzate con Poppler e ispezionate: nessun taglio/overlap/footer fuori pagina. Fixture arabo ha richiesto correzione spacing RTL e separazione prezzo/font Latin, poi ispezionata senza glyph euro mancanti. Questa prova non equivale a verifica di ogni lingua/font/modalità. Test reali isolamento DB e QA browser sono gate separati in ownership verifier/root.
