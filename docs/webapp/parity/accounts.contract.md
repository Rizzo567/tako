# Operational account and reservation contract — implementation in progress

`webAccountRoutes` mounts at `/api/web-accounts`. `POST /forgot-password {email}` returns generic response regardless of account/provider state. Reset token SHA256 only in `web_password_resets`, 30-minute expiry. Direct mail delivery (not persisted raw token), `WEB_ORIGIN` HTTPS fixes link origin; `WEB_EMAIL_ENABLED=1`, `RESEND_API_KEY`, `EMAIL_FROM` required for actual delivery. Tests inject `webAccountRoutesWithDelivery(fake)`, no emails to real people. `POST /reset-password {token,password}` consumes atomically, updates password, clears appliance secret and revokes every user session. `GET /capabilities` reports email configuration and `cardGuarantee:false` honestly. Delivery failures invalidate created token; generic reply does not claim successful delivery.

Reservation helper takes restaurant advisory lock before table locks in every transaction. `checkReservationCapacity(tx,input)` checks active-table seats and aggregate concurrent parties; cancelled/no_show excluded, requested/confirmed/seated count. Optional positive `settings.reservationCapacity` capped by total active seats. Sweep-line evaluates overlapping occupancy correctly, adjacent intervals do not collide. Public reservation caller MUST lock/check/insert inside same transaction. `reservationLocalInstant` converts strict date/time/fuso, rejecting DST gaps and repeated ambiguous times unless caller offers explicit-offset alternative. `nextCalendarDay` supports real 23/25h day boundaries.

Open gates: operational registration route, durable reminder outbox processor, real DB reset/capacity tests and complete browser flows. Existing exported factory is implementation, not a declaration of completed parity. Provider activation disabled by default; no Stripe guarantee implemented.
